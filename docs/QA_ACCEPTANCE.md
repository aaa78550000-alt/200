# 品質驗收與自動截圖規則

## 完成定義
- 能真實操作；若 M0 demo，明確標示為 demo，不假冒 API 成功。
- M1 起資料從後端取得並持久化；重新整理後不遺失；成功提示必須由 API 結果支持。
- 預約並發、權限、付款重試和契約歷史要有自動測試。
- 手機 375/390、平板 768/1024、桌面 1440 不會功能遮蔽或橫向溢出。
- 空資料、載入、網路失敗、權限不足及表單錯誤皆有合理提示。
- 每個 UI 模組保存執行截圖（例如 `artifacts/screenshots/today-mobile.png`），非審核通過的圖片不可直接做 CI 基準。

## 強制 E2E
E01 新店家註冊→新增服務/員工→建立虛構毛孩；E02 毛孩照片/注意事項/最近體重；E03 搜尋重名毛孩辨識；E04 熟客預約；E05 同時搶同一時段最多一筆確認；E06 美容師請假影響新申請和既有預約警示；E07 改期保留 id 和歷史；E08 報到開始完工待接回；E09 已付款但仍待接回；E10 交接後才 completed；E11 部分付款／退款；E12 同一付款請求重試不重複扣；E13 已簽約版本更改保留原證據；E14 LINE 失敗預約不受影響；E15 跨店個資/照片/契約 API 存取拒絕；E16 手機完整四步預約；E17 斷網不得假成功；E18 飼主不得靠姓名電話讀他人資料。

實作對照表見 `docs/HANDOFF.md`「測試覆蓋」。

## 視覺驗收步驟
1. 建立 deterministic seed，固定日期/時區/照片/內容；使用 demo fixtures。
2. 啟動 dev server 並等 HTTP、字體、圖片及業務資料都已可用。
3. Chromium 視窗 390x844、1440x900，補測 375x812、768x1024、1024x768。
4. 對五頁及一個關鍵展開狀態截圖；檢查 console error/水平溢出/觸控目標。
5. 由另一個上下文評審（若有子代理）或自我評審，簡列 1~3 最大問題；最多修兩輪。
6. 檢查前後圖，將 evidence 放 `artifacts/visual/`，更新 `docs/UI_REVIEW.md`；不自動更新 approved baseline。
7. 另外執行鍵盤/焦點/色彩對比/reduced-motion 等可及性驗收。

## Performance 與操作效率假設
熟客建立預約 <30 秒、正常完工 <30 秒、照護注意事項打開預約即見、歷史服務 1~2 次操作可達；以真實測試和紀錄確認，不能宣稱已達標。若失敗先改工作流程，不只換顏色。

## 視覺截圖不能證明
截圖不等於功能、RLS、法規、性能、營運可靠度通過；這些有獨立 QA Gate。任何未執行測試要明確標記 NOT RUN。
